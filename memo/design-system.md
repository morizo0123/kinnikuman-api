# デザインシステム / テーマ メモ

## CSS 変数ベースのテーマ設計(shadcn 流)

### 基本構造

1. CSS 変数で「テーマ」を定義(:root, .dark)
   ↓
2. Tailwind クラスで「役割」を当てる(bg-primary, text-muted-foreground)
   ↓
3. 結果が画面に出る

### 役割ベース命名の利点

- `bg-red-500`(固有色)ではなく `bg-primary`(役割) を使う
- → ダークモード対応がほぼ無料
- → 後でテーマ変更が一発(`--primary` の値を変えるだけ)
- → 「ブランドカラー」概念がコードに残る

### 変数を変えるだけでは色は変わらない

- CSS 変数は「定義」、Tailwind クラスは「使う場所」
- 両方を揃えて初めて反映される
- 例: ロゴを赤くしたい → `text-primary` クラスを当てる

## shadcn の主要 CSS 変数

| 変数                                 | 役割                        |
| ------------------------------------ | --------------------------- |
| `--background` / `--foreground`      | 全体の背景 / 文字           |
| `--card` / `--card-foreground`       | カードコンポーネント        |
| `--primary` / `--primary-foreground` | メインカラー(ボタン、ロゴ)  |
| `--secondary`                        | 控えめな背景                |
| `--muted` / `--muted-foreground`     | 控えめな背景 / 副次テキスト |
| `--accent` / `--accent-foreground`   | ナビホバー、active          |
| `--destructive`                      | 警告(削除など)              |
| `--border` / `--input`               | 枠線、入力欄                |
| `--ring`                             | フォーカス時の輪郭          |

## カラー指定: oklch とは

```css
--primary: oklch(0.55 0.25 27);
```

- shadcn の新バージョンで採用された色空間
- `L`(明度) `C`(彩度) `H`(色相)
- HSL や RGB より「知覚的に均一」=同じ数値差で同じ見た目の差になる
- `oklch(0.55 0.25 27)` ≒ `#dc000c`(深い赤)

## Stripe デザインシステムの特徴(参考にした要点)

- **純白背景 + 極薄クールグレー**(`#FFFFFF` + `#F6F9FC`)
- **深いスレートの文字**(`#0A2540`、絶対黒を避ける)
- **プライマリ色は1色だけ、使いすぎない**
- **トークン数を抑える**ことで一貫性
- **微妙な box shadow** でエレベーション

→ 今回は「Stripe スタイル + キン肉マン赤(#dc000c)」

## ダークモードの実装

### 仕組み

<html class="dark"> ← この class があるとダークモード
  ↓
.dark { --background: 暗い色; ... } ← CSS 変数が暗色に切り替わる
  ↓
bg-background などのクラスが暗くなる

つまり「html タグに dark class を付け外しする」だけ。

3状態の管理

- light — 常に明るい
- dark — 常に暗い
- system — OS の設定に追従(推奨)

## useEffect のクリーンアップ

```ts
useEffect(() => {
  // 副作用(リスナー登録、購読、タイマーなど)
  return () => {
    // クリーンアップ(後片付け)
  };
}, [deps]);
```

### クリーンアップが呼ばれるタイミング(3つ)

1. 依存配列の値が変わって、再実行される直前
2. コンポーネントがアンマウントされるとき
3. React StrictMode の開発時2回実行

### イベントリスナー登録時の鉄則

```ts
// 同じ関数参照を渡す
const handler = () => { ... }
element.addEventListener('change', handler)
return () => element.removeEventListener('change', handler)
```

- add と remove には同じ関数参照を渡す必要がある
- アロー関数を毎回作ると削除できない(別物扱い)

### リスナーとクリーンアップは別物

- リスナー本体: イベント発火のたび何度でも呼ばれる
- クリーンアップ関数: useEffect の再実行 or アンマウント時に1回だけ呼ばれる
- 名前で混同しやすいが、役割が違う

### クリーンアップを書かないと

- リスナーが残り続けてメモリリーク
- 同じイベントで何度も呼ばれる
- 「再レンダリングのたびにリスナーが増える」バグ
